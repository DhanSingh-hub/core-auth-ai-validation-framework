# Phase 1 — Single-Leg Examples (one chain per ATL105 segment)

## What this is

One full **Requirement → Business Scenario → Test Case → Test Data** chain per
segment in the ATL105 global segment catalog (`knowledge_base.json["segments"]`,
49 segments total), generated by calling the **real pipeline modules directly**
(not hand-typed, not copied from any prior run's output under `logs/**`):

| Stage | Real function called | Source file |
|---|---|---|
| Requirement | `_structural_field_requirements()` | `src/pipeline/step5_requirements/extractor.py` |
| Scenario | `build_business_rule_scenarios()` | `src/pipeline/scenarios/generator.py` |
| Transaction resolution | `TransactionResolver.resolve()` | `src/pipeline/test_generation/transaction_resolver.py` |
| Test Case | `compose_test_case()` / `compose_request()` | `src/pipeline/test_generation/composer.py` |
| Expected Response (oracle) | `build_expected_response()` | `src/pipeline/test_generation/expected_response_builder.py` |
| Verification | `verify_with_bounded_retry()` | `src/pipeline/test_generation/verification_agent.py` |
| QE-shaped test data | `build_test_case_documents()` / `write_documents()` | `src/pipeline/test_generation/qe_shaped_test_data.py` |

Generator script: [generate_single_leg_examples.py](generate_single_leg_examples.py).
Re-running it reproduces every file in this folder byte-for-byte (deterministic —
no randomness, no LLM call anywhere in the script).

## Why this is NOT a full pipeline run

`run_pipeline.py` / `extractor.run()` / `generator.run()` / `composer.run()` process
the **entire** spec catalog (thousands of elements → thousands of scenarios →
thousands of test cases), write into the real `candidates/`/`approved/` stores, and
require the LLM bridge for the narrative/business-rule-phrasing/flow paths. This
script calls only the **deterministic, LLM-free building-block functions** those
stages are built from, scoped to exactly one representative requirement per
segment, and writes exclusively under this folder — the real pipeline's own
candidate/approved catalogs are never touched.

## Folder structure

```
phase_1_single_leg/
  generate_single_leg_examples.py   # the generator (re-run any time)
  INDEX.json                        # one row per segment: OK or a documented gap
  requirements/requirement_candidates.json   # all 47 requirements (every segment that
                                              # produced one — includes the 10 segments
                                              # whose scenario later hit a transaction gap)
  scenarios/candidate_scenarios.json         # all 47 scenarios built from those requirements
  test_cases/test_case_candidates.json       # the 37 that reached a composed test case
                                              # (each with expected_response + verification)
  test_data/TC-NNNNNN.json          # QE-shaped wire message (what a tester sends)
  test_data/TC-NNNNNN.meta.json     # per-field traceability (source, dataSource, page)
  chains/segment_<NUM>.json         # ONE combined file per segment — the easiest
                                     # single artifact to hand to a reviewer for
                                     # that segment (requirement+scenario+test_case,
                                     # or the gap explanation if none exists)
```

## Result: 37 of 49 segments have a full chain; 12 are documented gaps

47 segments produced a requirement + scenario; 37 of those also reached a composed
test case + test data (the remaining 10 have a real scenario but the transaction
resolver could not safely place them — see the gap table below). 2 segments
(116, 155) produced no requirement at all.

Every gap below is a **real, currently-existing limitation of the pipeline's
deterministic logic on this spec extraction** — never a fabricated value. See
`INDEX.json` for the exact reason recorded against each segment.

| Segment(s) | Gap reason |
|---|---|
| 116 | `GAP_NO_FIELDS` — knowledge_base.json has zero extracted fields for this segment (TransArmor Load Data Segment); nothing to derive a requirement from. |
| 155 | `GAP_NO_REQUIREMENT_DERIVED` — Real Time Account Updater Response Segment's extracted "fields" are malformed (repeating Table ID/Table Length/Table Data rows with an empty `roc`, not R/O/C) — a pre-existing spec-extraction quality issue, not something this script can safely paper over. |
| DL7, DL8, 139, 140, 141, 149, 150 | `GAP_RESOLVER_FALLBACK_UNRELIABLE` — these 7 segments are not listed as a segment of **any** transaction in `atl105_complete_templates.json` today (Moneris Day End Batch/Fuel Price Update/EMV Terminal Floor Limits/Supplemental Terminal segments) — verified directly against the templates, not inferred. |
| 118, 119, 142 | `GAP_RESOLVER_FALLBACK_UNRELIABLE` — the real `TransactionResolver` only resolves scenarios with empty `parameters` (true for every `field_constraint` scenario) via a union-of-transactions fallback across the requirement's related elements, capped at 6 results (`max_fallback_transactions_per_scenario`) and sorted alphabetically. For these 3 segments every transaction that union produced was a false positive (verified against the transaction's own real segment list) — the genuinely correct transaction exists but was outside the alphabetical top 6. This is a real, reproducible limitation of the current deterministic resolver, worth raising with the pipeline team; it is not fixed here to avoid guessing which transaction is "right" beyond what the codebase itself can prove. |

Each gap segment still has its **requirement** derived and included in
`requirements/requirement_candidates.json` and its own `chains/segment_<NUM>.json`
(with the requirement plus the gap explanation) — only the scenario/test
case/test data steps are withheld for the segments the resolver can't safely place
(116 and 155 have no requirement either, for the reasons above).

## How to read one chain

Open `chains/segment_100.json` for a worked example (Standard Message Data
Segment → Terminal Identifier is required). It contains, in order:
`requirement` (why this must be tested, spec page cited), `scenario` (the positive
business-rule scenario built from it, oracle authority disclosed), `test_case`
(the fully composed request across every segment of the real transaction
template it resolved to, e.g. `ECA/TeleCheck Service Transaction Request`, with
`expected_response` and `verification` attached). The matching wire-format
message a tester would actually send is `test_data/<test_case.id>.json`, with
per-field provenance in the sibling `.meta.json`.

## Methodology note: why one field per segment, and which one

Each segment can have many Required fields; this deliverable picks exactly ONE
representative Required field per segment (the first one, in spec order) as the
scenario's anchor, preferring a segment-specific field over a ubiquitous envelope
field (Segment Type / Segment Length / Information Byte — present in nearly
every segment) so the real `TransactionResolver`'s fallback match stays as
precise as the deterministic pipeline logic allows (see `transaction_resolver.py`
`KNOWN_UBIQUITOUS_ELEMENT_NOS`). The **composed test case still includes every
other field of every other segment in that transaction**, exactly as the real
Composer would — this is not a single-field test case, only a single-field
*anchor* for traceability.
