## 1. Why These Documents Were Ingested

ATL105 2026-4 Section 3.3 Telecommunications Requirements (PDF p.49, printed p.3-2; `extracted_text_new.txt` lines 2805-2815) lists three companion sources for connectivity. The third one is:

> "For additional Internet support information, please refer to the Secure Transport section on the First Data® Web site (https://www.firstdata.com/en_us/customer-center/merchants/support/secure-transport-api)"

The 2026-3 text is identical (`extracted_text.txt` lines 2621-2623), so there is no version drift. ATL105 names no document, version or section beyond that pointer, and the pointer is unusable today:

- The clickable link in the PDF goes to `https://www.firstdata.com/en` only. The full path is printed but not linked.
- The printed URL now redirects to the generic Fiserv merchant customer-center page (`https://merchants.fiserv.com/en_us/customer-center.html`). On 2026-10-28 that page refused the request (HTTP 403), so the Secure Transport section could not be retrieved ([GAP-ST-01](#12-gaps-and-missing-references)).

Before this ingestion the Test Solution had no Secure Transport knowledge. The [chapter-family coverage gap register](../specs/kb/chapter-coverage-gap-register.md) records Chapter 3 as "Not wholly N/A" for its TPP/VAR, terminal-identity and telecom thresholds. Nothing covered the Internet path that Section 3.3 delegates.

On 2026-10-28 the user supplied 13 Secure Transport files:

- `SecureTransport-UnixSrc-API.pdf` and `SecureTransport-XML-API.pdf`, the two generic guides
- the folder `Secure_Transport_Guide/`, which is the Datawire Secure Transport package for Rapid Connect

The user asked for every document to be read and split chapter-wise or phase-wise so that no detail is missed, ingested, trained, and remembered in the strategy. The user chose documentation-level training, as was done for the EMV guide. The confidential sources and their verbatim split stay local because this repository is public.

**What was done:**

1. **Stored, split and verified.** The files were stored byte-for-byte and hash-pinned, then extracted and split into 107 chapter/phase files: 292 PDF pages plus 2 Word documents, 2 schemas and a READ_ME.
   - Every split is proven complete: the chapters of each document concatenate to exactly its full extracted text.
   - The 19 pages with diagrams or screenshots were rendered and read.
2. **Read in full.** Four independent readers covered every line, and their quotations were machine-checked. The digests are kept locally.
3. **Trained into this record.** This record holds the source binding, applicability rules, the chapter map, a rule catalog, reference tables, the ATL105 integration map, scenarios, conflicts, SME queries, gaps and a backlog.
4. **Wired into memory.** The record is linked from the strategy, the handbook, the KB, `training-status.json` and the communication register (`TT-0016`).
5. **Made repeatable.** The checks are `scripts/build-secure-transport-ingestion.py` and `scripts/verify-secure-transport-ingestion.py`.

## 3. Applicability, Precedence and Evidence Rules

These rules are mandatory whenever the Test Solution uses Secure Transport knowledge.

| Topic | Rule |
| --- | --- |
| Precedence | ATL105 governs the content of every ATL105 message. Secure Transport only carries that message: the generic guides say the network "never reads or interprets the payload in any way" (ST-UNIX-API p.28) and "The payload is not read or interpreted by the Secure Transport Network." (ST-XML-API p.60). Secure Transport knowledge never adds, removes or overrides an ATL105 field, segment, length or response-code rule. A conflict is logged here and ATL105 is enforced. |
| What Section 3.3 binds | Section 3.3 points to a web section, not to a document. The two generic guides are the most likely content of that section, but this is an inference ([Q-ST-01](#11-open-sme-queries)). Until an SME confirms it, every rule here stays `PROVISIONAL`. |
| Document families | **GENERIC** (ST-UNIX-API, ST-XML-API) describes how any processor's native message is carried. It applies to an ATL105 payload. **RAPID_CONNECT** (the other 11 files) describes the same network for the Rapid Connect host. It is informative only for BUYPASS. |
| Rapid Connect values never transfer | Never apply these to BUYPASS without SME confirmation: `App` `RAPIDCONNECTSRS`; `ServiceID` `160`; the AuthKey1/AuthKey2 formats; the 14-character `ClientRef` ending in a TPP ID; the `xml_escape`/`cdata` encodings of a Rapid Connect XML payload; Rapid Connect URLs, hosts and IP addresses; the ClientTimeout ranges; the UMF EchoTest ban; the certification forms. Their rules carry scope `RAPID_CONNECT`. |
| Shared transport behaviour | Some behaviour is stated in both families: HTTPS POST on outbound TCP 443, DNS without IP pinning, the trusted root certificate, SRS registration and activation, service discovery, StatusCode/ReturnCode semantics, session mechanics, retry and time-out-reversal tables, and keep-alive. It may be used as `REVIEW` evidence for BUYPASS Internet connectivity. Where the families differ, both rules are kept and the difference is a conflict ([section 10](#10-source-conflicts-and-defects)). |
| Security baseline | The generic guides predate the current baseline. ST-UNIX-API (2015) enables TLSv1, TLSv1.1 and TLSv1.2 by default and states no cipher or host-name rule. The 2021-2022 Rapid Connect documents require TLS 1.2 with four AES-GCM suites, the DigiCert Global Root CA and Global Root G2, and RFC 6125 host-name verification. Expect the stricter baseline (`REVIEW`) for any Internet client, but do not report it as a BUYPASS certification requirement until an SME confirms it ([Q-ST-05](#11-open-sme-queries)). |
| Status | Rules are `PROVISIONAL` and documentation-level. They are never counted in ATL105 rule coverage, the canonical denominator or certification. **MUST**/**SHOULD** rules become FAIL/REVIEW candidates only after SME confirmation and an executable harness ([section 13](#13-implementation-backlog)). **INFO** rules describe values and network behaviour. |
| Provenance | A rule carries a transport anchor (`SECURE-TRANSPORT` / document ID / version / page, phase or line), never an ATL105 `sourceAnchor`. Matching of AI artifacts against Test Solution artifacts stays keyed on ATL105 anchors. |
| Scenario readiness | `ARTIFACT_REVIEW`: checkable offline on captured envelopes, configurations, logs or AI artifacts. `CERTIFICATION_ENVIRONMENT`: needs a client run against a Datawire staging service. `SME_CONFIRMATION`: blocked until BUYPASS-specific values are confirmed. |
| Evidence integrity | Every quotation of 18 characters or more is verbatim and machine-checked. Every rule quotation is on the page, phase or lines its rule cites. Content that exists only in images (for example the Service Discovery refresh interval in the ST-XML-API p.8 and p.30 flowcharts) is read from the rendered page and marked as image-derived. |
| Confidentiality | The sources, their text and the verbatim split stay in the git-ignored `docs/specs/secure-transport/`. Tracked files hold only identities, hashes, structure, short cited quotations and derived knowledge. |

## 5. How Secure Transport Works

Secure Transport (VXN, branded Datawire) is an Internet transport between a point-of-sale application and a payment processor's host. The application wraps the host message it would otherwise send over a dial-up or frame-relay circuit in an XML version 3 envelope. It posts the envelope over HTTPS to a Secure Transport service provider and receives the host's response in the same kind of envelope.

The network routes by `ServiceID` and authenticates the client by `DID`. It does not interpret the payload (ST-XML-API p.7, p.9, p.60; ST-UNIX-API p.9, p.28).

| Phase | What happens | Generic guides (ST-UNIX-API, ST-XML-API) | Rapid Connect package |
| --- | --- | --- | --- |
| 1. Network access | HTTPS on outbound TCP 443, resolved by DNS | No IP pinning. Edge nodes are found through DNS (ST-UNIX-API p.59; ST-XML-API p.74). | Same rule, plus published staging hosts and IPs and a production IP contact (ST-RC-PARAMS p.3; ST-RC-GUIDE p.7-8). |
| 2. Trust set-up | Trusted root certificate and TLS protocol versions, before any request | Loading the CA certificate is mandatory (`VxnSetCA`; otherwise error 62). TLSv1, TLSv1.1 and TLSv1.2 are enabled by default (ST-UNIX-API p.16-18, p.43, p.45). | TLS 1.2 with four AES-GCM suites, DigiCert Global Root CA and Global Root G2, and RFC 6125 host-name verification (ST-RC-TLS p.2; ST-RC-ROOTCA p.2; ST-RC-CERT-FORM §06). |
| 3. Provisioning, once per merchant/terminal | Self-registration (SRS) obtains the `DID` | Service Discovery for the SRS URL, then Registration with MID and TID, then save the DID, then Activation immediately. `Retry` means resend after 30 seconds, 3-5 times. `AccessDenied` follows a repeat after activation (ST-XML-API p.19-29, p.70-71; ST-UNIX-API p.19-24). | The same flow over XML or SOAP. The DID and transaction URL are saved permanently and securely, and activation must follow at once (ST-RC-SRS pp.8-30; ST-RC-SRS-STEPS p.2). |
| 4. Start-up | Find the fastest service provider | Service Discovery returns service-provider URLs; repeat requests use a conditional GET. Every URL is pinged, and the fastest becomes the active URL (ST-XML-API p.30-39, p.56). The flowcharts show a refresh every 6 to 24 hours (images on p.8 and p.30). | XML clients start from the SRS Service Discovery URL; SOAP clients start from the WSDL (ST-RC-SRS-STEPS p.2; ST-RC-PARAMS p.2). |
| 5. Transaction | Simple or Session | **Simple**: `Transaction` holds `ServiceID` and `Payload`. **Session**: `InitiateSession`, then `SessionTransaction` messages using `SessionContext`, then `TerminateSession`, one outstanding request at a time. The payload is the processor's native message, encoded `datawire` (the default; `\|`-hex escapes) or `base64` (ST-XML-API p.40-55, p.76; ST-UNIX-API p.25-38). | Same structure (`rcxml.xsd`). The payload is a Rapid Connect XML message, encoded `xml_escape` (the default) or `cdata` (ST-RC-GUIDE p.17; ST-RC-XSD-RCXML lines 19-32). |
| 6. Outcome | Three layers | 1. HTTP status. 2. `StatusCode`: `OK` means the request passed through the network. 3. `ReturnCode`: `000` means success; the other codes are network or host-connection errors. The host's own approval or decline is inside the payload (ST-XML-API p.69-73). | Same layering. `OK` alone is not success (ST-RC-GUIDE p.27, p.87-89). |
| 7. Recovery | Retry, URL fail-over, time-out reversal | Each status and return code says whether the processor may have received the request, whether to retry, whether to fail over and whether a time-out reversal is needed. Errors mid-session end the session; the session is then restarted (ST-XML-API p.70-73; ST-UNIX-API p.61-63). | Return codes 200-206, 405, 505, 006 and 008 each have a retry and reversal rule. Clients make at most 3 automatic retries and log codes unchanged (ST-RC-GUIDE p.86-88; ST-RC-CERT-FORM §07). |
| 8. Certification | Compliance evidence before production | Not described | Compliance test form (Sections 1-7 plus an audio test) or the re-certification script. Evidence includes screenshots, Wireshark traces, a fake-host name test and a 125-transaction session batch (ST-RC-CERT-FORM; ST-RC-RECERT). |

**What this means for ATL105 testing.** An ATL105 request or response is the opaque payload. Its validation stays under ATL105.

Secure Transport adds transport-level expectations that the ATL105 validators do not cover:

- payload size and encoding
- envelope identifiers
- TLS and certificates
- outcome interpretation
- retries and time-out reversals

These are catalogued in [section 6](#6-rule-catalog) and tied to ATL105 in [section 8](#8-atl105-integration-map).

| Encoding | Family | Rule | Source |
| --- | --- | --- | --- |
| `datawire` | Generic (the default) | Every byte that is not a letter or digit is written as `\|` plus two hex digits; `\|` itself becomes `\|7C`. Examples: FS (0x1C) is `\|1C`, `@` is `\|40`. | `base64` | Generic | Base64 of the payload bytes | ST-XML-API p.40, p.60 |
| `xml_escape` | Rapid Connect (the default) | `<`, `>` and `&` replaced by entities; encode exactly once | ST-RC-GUIDE p.17 |
| `cdata` | Rapid Connect | The raw message wrapped in `<![CDATA[` ... `]]>`. It must not contain `]]>`. | ST-RC-GUIDE p.17; ST-RC-CERT-FORM §06 |

## 10. Source Conflicts and Defects

Conflicts are kept, never resolved by guessing. In the **Detail and tester action** column, the text after **Do** is what a tester should do now.
