# Special Transaction-Type Training Technique

## Purpose

Use this method for Appendix G transaction types `9`, `D`, `E`, `K`, `L`, `M`, `N`, `Q`, `T`, and `V`. They are not standard financial transaction types, so do not generate their Test BRs by copying the Segment 100 financial single-step template.

## Training Sequence

1. **Classify the message family first.** Separate standard financial codes from special/nonfinancial operations. For type `9`, distinguish the Appendix G transaction category from the special Prompt Code operation values such as `900`, `901`, and `990`; do not conflate them.
2. **Read the authoritative operation source.** Use the exact Appendix G description and the dedicated Section 10 flow when available. A code/name alone may establish an operation identity, but not undocumented request/response behavior.
3. **Derive atomic Test BRs.** Split independent operations and outcomes into separate BRs: activation, balance inquiry, recharge limit, merge constraints, loyalty functions, and so on. Preserve the exact section, element, and rule anchors.
4. **Record evidence maturity.** Use `DIRECT_BEHAVIOR` when the source states observable behavior, `DIRECT_DESCRIPTION` for an operation label/summary, and `APPENDIX_G_ONLY` when only the table definition is available. Keep every draft `DRAFT_REVIEW_REQUIRED` until the remaining gates pass.
5. **Separate known behavior from external dependencies.** Code `D` currently has Appendix-G-only evidence for RBC Loyalty Lookup. Code `T` is TransArmor token registration, but ATL105 §10.12 delegates detailed processing to an external specification. Do not invent protocol, payload, token lifecycle, or response assertions.
6. **Build flow-specific scenarios.** For each BR, derive positive, negative, boundary, and conditional cases where supported. Model stored-value state changes across requests; model loyalty reversal against the prior approved operation; model special prompt request/response framing from its own source.
7. **Create independent synthetic JSON.** Test Data must be generated by the Test Solution, clearly synthetic, linked to the Test Case, and independent of AI-produced fixtures. Assert both the request and relevant response/state changes.
8. **Validate and hand off.** Check schema, source anchors, expected outcomes, complete BR -> TS -> TC -> TD links, fixture existence, and executable validators. Log user, machine, branch, evidence, blockers, and next action in the shared per-code ledger and its immutable event log.
