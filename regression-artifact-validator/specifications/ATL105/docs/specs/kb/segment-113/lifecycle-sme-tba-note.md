# Segment 113 Lifecycle and Correlation: SME and TBA Learning Note

Combines and scopes [Segment 100's Final Closure note](../segment-100/final-closure-sme-tba-note.md) and [Sequence Number and Lifecycle Correlation note](../segment-100/sequence-lifecycle-sme-tba-note.md) to the ECA/TeleCheck Service Transaction Request context. Segment 113 does not have separate "final closure" and "sequence lifecycle" concerns the way Segment 100 does, so this single note covers both.

## The Segment 113 Lifecycle

```text
Check purchase (original)
  -> Void (references the original via ECA/TeleCheck Trace ID, Element 134)
  -> Decline -> Denial Record (Denial Record Number, Element 136, referenced on a printed receipt)
```

Unlike a generic Financial Transaction's reversal/completion lifecycle (which correlates via Standard Segment's Sequence Number, Element 86, per Section 2.3.1's TOR rules), an ECA/TeleCheck Void request has its own **dedicated** correlation identifier: **ECA/TeleCheck Trace ID (Element 134)**, generated by the ECA/TeleCheck service host on the original transaction and echoed back on the Void.

| Lifecycle flow | Original transaction | Follow-up | Correlation identifier |
| --- | --- | --- | --- |
| Check purchase -> Void | Check purchase request | Void request | ECA/TeleCheck Trace ID (Element 134), per spec text: "must be present in all Void transaction requests" |
| Check purchase -> decline | Check purchase request (implicit) | Host response carries Denial Record Number | Denial Record Number (Element 136), referenced on the printed Denial Record Receipt (Section 10.8.5) |

This is a genuinely different correlation mechanism from Segment 100's Sequence-Number-based lifecycle rule — Segment 113's Void correlation lives inside Segment 113 itself (Element 134), not solely in Standard Segment's Sequence Number, even though the standard TOR/Sequence-Number rules from Section 2.3 may still apply at the message-transport level for timeout scenarios.

## SME Review Questions

1. Is this a check purchase (original), a Void, or a scenario following a declined transaction?
2. If this is a Void, does Segment 113's Trace ID match the original transaction's ECA/TeleCheck host-assigned trace ID?
3. If this is a declined transaction, does the printed receipt reference the correct Denial Record Number?
4. Does the Standard Segment's Sequence Number (Element 86) still follow the generic TOR reuse rule independently of the Trace ID correlation?

### Important Boundary

Do not assume a new Sequence Number implies a new, unrelated transaction for ECA/TeleCheck the way Segment 100's generic lifecycle rule states — for Segment 113, the AUTHORITATIVE correlation identifier for a Void is the ECA/TeleCheck Trace ID, not the Sequence Number alone. If the Trace ID is missing on what is claimed to be a Void request, classify the lifecycle relationship as `REVIEW_REQUIRED`; do not infer it from Sequence Number or file order alone.

## TBA Rule

```text
For every Segment 113 Void follow-up, the test data shall carry the ECA/TeleCheck
Trace ID (Element 134) matching the original check purchase's host-assigned trace
identifier. This condition is cataloged (SEG113-R-011) but not code-enforced by the
JSON payload validator, per SME direction (SEG113-SME-003).
```

## Current Validator Boundary

`Segment113PayloadValidator` validates Trace ID's type/length bound only (`SEG113-R-011`). It does not detect that a transaction is a Void, nor cross-check the Trace ID against a prior transaction's value — both remain manual/TBA review items.

## Review Checklist

- Is the transaction type (Void vs. original purchase) identifiable from context outside Segment 113 itself?
- Is Trace ID populated whenever the transaction is a Void?
- Does the Denial Record Number on a printed receipt match the host's returned value for a decline?
- Is the Sequence Number (Segment 100, Element 86) still reused correctly for any generic TOR/timeout scenario, independent of the Trace ID correlation?
