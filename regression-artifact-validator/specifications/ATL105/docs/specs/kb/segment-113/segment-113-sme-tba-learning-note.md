# Segment 113 ECA/TeleCheck® Data Segment: SME and TBA Learning Note

Verified against BUYPASS Platform ATL105 release 2026-3, sections 10.8, 11.3, 12.12, and 13.2 Elements 131-137.

## 1. What Segment 113 Means

Segment 113 is the **ECA/TeleCheck® Data Segment**. It carries check-service risk-control data (clerk ID, product code, phone number, trace IDs, denial record number, extended MICR data) used specifically when a merchant is processing a paper check through the ECA (Electronic Check Acceptance) / TeleCheck® service. Like Segment 108 (Loyalty), Segment 113 belongs to its own dedicated **ECA/TeleCheck® Service Transaction Request** message family — it is not a Financial Transaction Request companion.

```text
TCP/IP header
  + Data Section 1: ATL105 identity and segment count
  + Data Section 2: Segment 100 standard transaction data
  + Data Section 3: Segment 110 (Check Data, required) + Segment 111 (Variable Information, optional)
                    + Segment 113 (ECA/TeleCheck Data, conditional)
```

## 2. Segment 113 Layout

| Field | Element | Length | Status | SME meaning |
| --- | ---: | ---: | --- | --- |
| Segment Type | 85 | 3 | Required | Fixed value `113` |
| Segment Length | 84 | 3 | Required | Encoded length of Segment 113, including its separators |
| ECA/TeleCheck Clerk ID | 131 | 6 | Required | Identifies the clerk processing the check |
| ECA/TeleCheck Product Code | 132 | 6 | Conditional | Merchandise-type code used by ECA/TeleCheck risk control (no documented enum — free-form) |
| ECA/TeleCheck Phone Number | 133 | 10 | Optional | Check writer's phone number |
| ECA/TeleCheck Trace ID | 134 | 22 | Conditional | Trace ID generated by the ECA/TeleCheck host; required on Void requests |
| Merchant Trace ID | 135 | 25 | Optional | Merchant-assigned identifier for the customer |
| Denial Record Number | 136 | 7 | Conditional | Reference number printed on a Denial Record receipt for a declined transaction |
| Extended MICR Data | 137 | 65 | Conditional | Supplements Segment 110's MICR Data (Element 122) when raw MICR exceeds 50 bytes |

Maximum Segment 113 length is **156 alphanumeric characters**. Fields are serialized in straightforward ascending element order (131→137) — no reordering quirk like Segment 108's Payment Tender Type/Track 2 Data reversal.

### Serialization rule

All fields are separated by Field Separators. When a field is not populated, still send the Field Separator.

## 3. When Segment 113 Is Required

Segment 113 is present in an ECA/TeleCheck® Service Transaction Request when the merchant needs to send ECA/TeleCheck-specific risk-control data. This is a genuine spec-inconsistency point: Element 63's (Number of Segments) processing-rule summary text names only Segments 110 and 111 for this message family, but Section 11.3.1's own request layout table explicitly includes Segment 113 alongside them. SME intake resolved this in favor of Section 11.3.1 — Segment 113 is a real, documented member of the request, and Element 63's summary is simply incomplete.

## 4. Check Processing Context (Section 10.8)

- ECA/TeleCheck service requires MICR data for swiped entries, and driver's license + State Code for manual entries (Section 10.8.1).
- A merchant authorization receipt and a check-writer's copy must be printed for each approved ECA/TeleCheck transaction, including the ECA/TeleCheck Service Trace ID, Approval Number, and the ECA/TeleCheck Acceptance Statement (Section 10.8.4).
- A **Denial Record Receipt** (Section 10.8.5) is printed for declined transactions, referencing the Denial Record Number (Element 136) — an alternative to TeleCheck's pre-printed Denial Record receipt form (TML-1791-R).

## 5. Cross-Segment Relationship: Extended MICR Data

Element 137 (Extended MICR Data) lives in Segment 113's own field layout (field 9), but its documented purpose is to **supplement** Element 122 (MICR Data) in a **different** segment — Segment 110 (Check Data Segment) — whenever the raw MICR data exceeds 50 bytes. This is a genuine cross-segment (110↔113) dependency. Per SME direction, the payload validator does not enforce this relationship across segments; it is cataloged only (`SEG113-R-014`).

## 6. POS Flow Examples

### Standard ECA/TeleCheck check purchase

```text
Clerk scans items
  -> Consumer presents a paper check
  -> Clerk swipes the check (MICR data captured) or keys it manually
  -> Device sends ECA/TeleCheck Clerk ID, Product Code, Phone Number
  -> Segment 100 carries standard transaction identity/amount
  -> Segment 110 carries the Check Data (MICR, driver's license if manual entry)
  -> Segment 113 carries the ECA/TeleCheck risk-control data
  -> Approved: merchant + check-writer receipts printed per Section 10.8.4
```

### Void transaction

```text
Clerk selects Void for a prior ECA/TeleCheck transaction
  -> Device populates ECA/TeleCheck Trace ID (134) with the original transaction's trace ID
  -> Segment 113 sent with Trace ID populated (spec requires it on all Void requests)
  -> Host matches and voids the original transaction
```

### Declined transaction (Denial Record)

```text
ECA/TeleCheck transaction is declined
  -> Host returns a Denial Record Number (136)
  -> Device/POS prints a Denial Record Receipt per Section 10.8.5, referencing that number
```

## 7. Validator Rules Implemented (`Segment113PayloadValidator`)

- Segment type is exactly `113` (`SEG113-R-003`).
- Segment 113 requires a Standard Segment (100) sibling within an ECA/TeleCheck Service Transaction Request (`SEG113-R-001`, `SEG113-R-002`).
- Segment length is 3 digits and within `001-156` (`SEG113-R-004`, `SEG113-R-005`).
- ECA/TeleCheck Clerk ID is required and alphanumeric max 6 (`SEG113-R-008`).
- ECA/TeleCheck Product Code, Phone Number, Trace ID, Merchant Trace ID, Denial Record Number, and Extended MICR Data follow their documented type/length bounds when populated (`SEG113-R-009` through `SEG113-R-014`).
- Segment 113 appears at most once per message (`SEG113-R-015`).

Rules not enforced in code (cataloged only, per SME direction or because they are wire-serialization/cross-message/cross-segment concerns): `SEG113-R-006`, `SEG113-R-007` (wire field order/separators), the Void-requires-Trace-ID condition within `SEG113-R-011`, the cross-segment Extended-MICR-Data condition within `SEG113-R-014`, `SEG113-R-016`, `SEG113-R-017`, `SEG113-R-018`.

## 9. SME Checklist

When reviewing an AI-generated ECA/TeleCheck artifact, ask:

- Does the artifact treat Segment 113 as belonging to a distinct ECA/TeleCheck Service Transaction Request, not a Financial Transaction Request companion?
- Does it correctly treat Segment 113 as conditional (not always required) within that request?
- Does it avoid inventing an enumeration for ECA/TeleCheck Product Code?
- Does it leave the Void-requires-Trace-ID and cross-segment Extended-MICR-Data conditions as business-rule documentation rather than expecting code-level enforcement?
- Does it require manual review where the specification has not defined a segment combination (e.g., Segment 113 with 101/102/103/108)?
