# Appendix Y — 3-D Secure

## Scope and source

This training covers ATL105 2026-3 Appendix Y-1 through Y-3, related Appendix I definitions for
Tables 035 and 036, and Segment 123 Element 237. Appendix Y describes 3-D Secure authentication for
Visa Verified by Visa, MasterCard SecureCode/Identity Check, and American Express SafeKey. It also
mentions Discover in the general discussion, but does not provide a Discover cryptogram mapping.

The executable oracle is
[`AppendixYSecureAuthenticationOracle`](../../../../../../src/main/java/com/coreauth/validator/canonical/AppendixYSecureAuthenticationOracle.java).
Its focused tests are
[`AppendixYSecureAuthenticationOracleTest`](../../../../../../src/test/java/com/coreauth/validator/AppendixYSecureAuthenticationOracleTest.java).
The source-traceable artifact inventory and synthetic data are in
[`appendix-y-segment-100-coverage.json`](../../../../../ATL105/test-output/test-json/appendices/appendix-y-segment-100-coverage.json).

## Source-derived message rules

- The response ECI/Terminal Type values documented for 3-D Secure are 25–29. Appendix Y's
  brand/cryptogram mapping is Visa/CAVV, MasterCard/AAV, and Amex/AEVV. The document's general
  mention of Discover is not sufficient to infer its mapping.
- The Visa scenario matrix is expressly not exhaustive:
  - Verified-by-Visa only: Table 035 CAVV data, 40 bytes (XID(20) + CAVV(20)).
  - Payment token only: revised CAVV in Element 195, 20 characters; TAVV is not applicable.
  - Verified-by-Visa plus Digital Wallet: revised CAVV in Element 195 and TAVV in Element 237.
    Element 237 is fixed at 28 characters and uses the documented Base64 alphabet.
- Element 195 is 20 bytes for Visa/Interlink tokenized transactions. This fact does not extend the
  Visa-only scenario matrix to Interlink.
- Amex SafeKey Element 203 is `SK` + a 28-character AEVV block + a 28-character AESK block. If
  AEVV is not applicable, its block is space-filled; the optional AESK block is also space-filled
  when not applicable. SafeKey is unavailable to OptBlue merchants.
- MasterCard AAV belongs in Segment 111 Table 036 UCAF Data. DSRP/token cryptograms belong in
  Segment 123 Element 237. When both cryptogram types are present, the first two UCAF Security Level
  positions must be `21`. Appendix I describes Security Level values `21` or `24`, a third position
  `0`–`7`, and the Table 036 subfield framing. No unsupported interpretation of undocumented data
  bytes is imposed by this oracle.
- MasterCard SecureCode requires a 3-D Secure v1.0.2-or-better compliant MPI.
- The Appendix Y narrative describes Acquirer, Issuer, and Interoperability domains and seven
  process steps. The actual protocol exchange, service behavior, and merchant availability are
  external to a Segment 100 payload.

Those seven steps are: cardholder entry of payment details; MPI initiation with the Directory
Server; routing to the Issuer ACS; return of the ACS response to the MPI; Issuer-hosted
cardholder authentication; issuer authorization response with cryptogram and applicable ECI; and
redirection to the merchant for purchase completion.

The source notes Visa token-service merchants may optionally support combined TAVV/CAVV and
records an October 2018 effective-date statement. It separately instructs merchants to confirm
availability with their First Data representative. Neither the historical date nor the optional
feature statement establishes current merchant enrollment.

Appendix I Table 036 provides the related UCAF details: Security Level positions 1-2 are `21` or
`24`, position 3 is `0`-`7`, and Table Data length is 3 or 35. When UCAF data is present it is 32
characters, framed as subfield ID `43` and length `28`; the spec says the data is for MasterCard
AAV and that removed Identity Check values `h` and `j` must not be sent. Appendix Y's Combined AAV
and DSRP rule is separately enforced as Security Level `21`.
The removed `h`/`j` values are recorded as a source constraint, but their precise data
representation is not guessed here and remains a manual review item.

## Oracle boundary and review gates

The oracle validates only source-supported structural values, field placement, and explicit
scenario combinations. It does not authenticate network cryptograms, prove that a cryptogram was
generated by the correct ACS/token service, establish successful protocol completion, or certify
merchant enrollment. Those claims require trusted external evidence. Discover's mapping and Visa
scenarios not listed in the non-exhaustive matrix remain review-required rather than guessed.

This package is therefore **PARTIALLY_COVERED**. Synthetic test data proves format and scenario
predicates only; it must not be described as genuine Visa, MasterCard, or Amex authentication data.
Interlink is deliberately not treated as Visa for Appendix Y scenario selection: Element 195's
Visa/Interlink applicability does not extend the Visa-specific scenario grid. Appendix I's
prohibition on removed MasterCard AAV values `h` and `j` is recorded as a review-gated requirement
because the oracle does not guess their precise data position or encoding. Feature availability
and merchant participation also remain external assessments rather than payload-level PASS results.
