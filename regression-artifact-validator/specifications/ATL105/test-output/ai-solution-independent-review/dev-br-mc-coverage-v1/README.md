## 6. Coverage definitions

- **COVERED**: The Dev BR explicitly states or models the requirement (scenario, code, flow leg, carried field, required segment or explicit source citation).
- **PARTIAL**: The Dev BR models part of the requirement, or models it with a defect or open gap.
- **CONTEXT_ONLY**: The Dev BR has the transaction context in which the requirement applies but does not state it; per-scenario 'supporting rules' are counts only and cannot be traced. Not counted as covered.
- **NOT_COVERED**: Neither the requirement nor a Dev scenario/dimension that expresses it exists in the Dev BR.
- **CONFLICT**: The Dev BR models something the specification restricts; needs SME decision.
- **NOT_APPLICABLE**: Not a Mastercard requirement (other network/card type or non-financial flow); excluded from the denominator.
- **EXTERNAL_SOURCE**: Governed by a source that is not in this repository; reported but excluded from the ATL105 denominator.


COVERED and PARTIAL require a Dev evidence pattern that the script finds in the delivery; NOT_COVERED and CONTEXT_ONLY claims carry search terms that must be absent from it. Spec items are computed from the Dev scenarios where possible (codes, entry modes, flows, carried fields) and curated otherwise.

## 8. Limitations

- Dispositions are curated Test Solution judgements (DRAFT_REVIEW_REQUIRED) pending SME/BA review.
- The Dev supporting rules are not delivered, so rule-level coverage cannot be measured; CONTEXT_ONLY marks that gap rather than assuming coverage.
- MasterCard Fleet scope depends on the Petroleum Industry Processing Specifications, which are not in the repository, and the trained solution has no Fleet context.
- The trained baseline is ATL105 2026-3; the compared sections are identical in 2026-4, but page numbers differ.
- Nothing was executed; no host, issuer or device outcome is confirmed.
