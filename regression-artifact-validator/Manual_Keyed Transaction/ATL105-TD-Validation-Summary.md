## What must be fixed

### 1. TC-001869 step 1 - The terminal is described two different ways in the same message

- **Test data file:** `test_data/TD-TC-001869.json`
- **Fields and values:** Table 031 (terminal capability) = `Table 005 = 018, Table 031 = 12`
- **What ATL105 says:**
  - Appendix I. Variable Information Data Layouts - Point-of-Service Terminal Capability Codes (Table 031), PDF p.569 (printed Appendix I-20): "12 = Hybrid Integrated Circuit Card Reader (Contact Chip & Contactless Chip) Capabilities"
  - Appendix I. Variable Information Data Layouts - Point-of-Service Terminal Capability Codes (Table 031), PDF p.569 (printed Appendix I-20): "07 = Contactless magnetic stripe read capability (no contact or contactless chip capability)"
  - Appendix J. Valid Point-of-Service Entry Mode Codes, PDF p.639 (printed Appendix J-2): "If a Contactless MSR is attached to the POS device and it has no chip capability, then all transactions will use Terminal PIN Entry Capability Mode code 8"
  - Appendix J. Valid Point-of-Service Entry Mode Codes, PDF p.639 (printed Appendix J-2): "8 Contactless Magnetic Stripe Read Capability"
  - Appendix J. Valid Point-of-Service Entry Mode Codes, PDF p.639 (printed Appendix J-2): "For EMV Contact and Contactless the valid PIN Entry Capability Mode code is 1 and not 8."
  - Appendix I. Variable Information Data Layouts - Point-of-Service Terminal Capability Codes (Table 031), PDF p.569 (printed Appendix I-20): "Once certified, the respective terminal capability values do not change regardless of the POS Entry Mode."
- **Why it is wrong:**
  - Table 005 '018' says: manual/keyed entry on a terminal with code 8 (contactless magnetic stripe read capability), which Appendix J note 1 reserves for a terminal with a contactless magstripe reader and no chip. Table 031 '12' says: hybrid reader: contact chip and contactless chip, so the terminal has a chip reader. Both cannot be true for the same terminal: a chip-capable terminal must send 1 (not 8), and a terminal without a chip cannot be 12. The test case itself says: "Terminal has a contactless (RFID) receiver attached and no chip reader; the card is swiped or keyed".
- **What it should be:**
  - Keep Table 005 = 018 and change Table 031 to 07, which means contactless magnetic stripe read (no contact or contactless chip). Use a separate RFID terminal, not the hybrid chip terminal used by the other test cases.

### 2. TC-001870 step 2 - Remaining-balance amount and Segment Length are wrong

- **Test data file:** `test_data/TD-TC-001870.step2.split-tender.json`
- **Fields and values:** Nonfuel Amount (test case value) = `08073891`; Segment Length = `082`; Nonfuel Amount = `<RemainingBalance = step 1 Nonfuel Amount - step 1 response Approved Amount>`
- **What ATL105 says:**
  - Element 58 Nonfuel Amount (Chapter 13), PDF p.393 (printed 13-53): "A maximum length of 7 bytes is allowed for all other card types."
  - Section 10.1.2.1 Partial Approval Transaction, PDF p.84 (printed 10-5): "Approved Amount (Element No. 6) contains the approved partial amount, and the POS device must prompt for payment of the remaining balance due on the sale."
  - Element 121 Partial Approval Indicator (Chapter 13), PDF p.440 (printed 13-100): "the network can approve an amount that is less than the amount in the Authorization request"
  - Element 6 Approved Amount (Chapter 13), PDF p.368 (printed 13-28): "Fixed length of nine digits with two assumed decimal places Zero-filled and right aligned"
  - Section 12.1 Standard Message Data Segment, PDF p.223 (printed 12-6): "Identifies the data segment's length, including Segment Type's length and Field Separators."
  - Element 84 Segment Length (Chapter 13), PDF p.406 (printed 13-66): "This figure is calculated using the lengths of all data elements in the segment plus all Field Separators/Product Data Field Delimiters related to those elements."
- **Why it is wrong:**
  - '08073891' ($80,738.91) has 8 digits. MasterCard amounts allow at most 7 digits; 8 digits are allowed for American Express cards only.
  - The original sale is $15.00 ('1500'). After a partial approval the remaining balance is the sale minus the approved amount, so it is always less than $15.00; '08073891' ($80,738.91) is impossible.
  - '082' is the length you get with the test case value(s) Nonfuel Amount '08073891'. With real values (amount 1 to 4 digits) the Segment Length can only be 075 to 078, so '082' can never be correct.
  - The field holds the instruction text '<RemainingBalance = step 1 Nonfuel Amount - step 1 response Approved Amount>' instead of a real Nonfuel Amount. BUYPASS cannot process this text, so the message cannot be sent until the real value from the step 1 response is filled in.
- **What it should be:**
  - Remaining balance = 1500 minus the step 1 response Approved Amount, leading zeros removed (for example Approved Amount 000001000 -> remainder 500).
  - Recalculate the Segment Length after filling in the real values (for example Approved Amount 000001000 -> amount 500 -> Segment Length 077).

### 3. TC-001871 step 2 - Reversal amount, Approval Number and Segment Length are wrong

- **Test data file:** `test_data/TD-TC-001871.step2.reversal.json`
- **Fields and values:** Nonfuel Amount (test case value) = `73622739`; Segment Length = `088`; Nonfuel Amount = `<NonfuelAmount from step 1 response>`; Approval Number = `<ApprovalNumber from step 1 response>`
- **What ATL105 says:**
  - Element 58 Nonfuel Amount (Chapter 13), PDF p.393 (printed 13-53): "A maximum length of 7 bytes is allowed for all other card types."
  - Section 10.1.2.1 Partial Approval Transaction, PDF p.84 (printed 10-5): "The amount in a Reversal (Void) request must be the amount approved in the original transaction response when a transaction has been partially approved."
  - Element 121 Partial Approval Indicator (Chapter 13), PDF p.440 (printed 13-100): "the network can approve an amount that is less than the amount in the Authorization request"
  - Element 6 Approved Amount (Chapter 13), PDF p.368 (printed 13-28): "Fixed length of nine digits with two assumed decimal places Zero-filled and right aligned"
  - Section 12.1 Standard Message Data Segment, PDF p.223 (printed 12-6): "Identifies the data segment's length, including Segment Type's length and Field Separators."
  - Element 84 Segment Length (Chapter 13), PDF p.406 (printed 13-66): "This figure is calculated using the lengths of all data elements in the segment plus all Field Separators/Product Data Field Delimiters related to those elements."
  - Element 5 Approval Number (Chapter 13), PDF p.368 (printed 13-28): "Required on reversals for matching information to the original purchase."
  - Element 5 Approval Number (Chapter 13), PDF p.368 (printed 13-28): "Fixed length of six alphanumeric characters; space-filled"
- **Why it is wrong:**
  - '73622739' ($736,227.39) has 8 digits. MasterCard amounts allow at most 7 digits; 8 digits are allowed for American Express cards only.
  - The reversal must carry exactly the amount approved in step 1. A partial approval is always less than the $15.00 requested, so '73622739' ($736,227.39) is impossible.
  - '088' is the length you get with the test case value(s) Nonfuel Amount '73622739', Approval Number '2J0775'. With real values (amount 1 to 4 digits; Approval Number always 6 characters) the Segment Length can only be 081 to 084, so '088' can never be correct.
  - The field holds the instruction text '<NonfuelAmount from step 1 response>' instead of a real Nonfuel Amount. BUYPASS cannot process this text, so the message cannot be sent until the real value from the step 1 response is filled in. Note: the step 1 response has no Nonfuel Amount field; the value comes from response Element 6 Approved Amount (9 digits, zero-filled), with the leading zeros removed.
  - The field holds the instruction text '<ApprovalNumber from step 1 response>' instead of a real Approval Number. BUYPASS cannot process this text, so the message cannot be sent until the real value from the step 1 response is filled in.
- **What it should be:**
  - Reversal amount = the step 1 response Approved Amount without the leading zeros (for example 000001000 -> 1000).
  - Recalculate the Segment Length after filling in the real values (for example Approved Amount 000001000 -> amount 1000 plus a 6-character Approval Number -> Segment Length 084).
  - Fill in at run time: Approval Number (Element 5) of step 1 response (p.368).
