# ATL105 Test Data Review - Key Findings (TC-001867 to TC-001871)

All page references are to the BUYPASS Platform ATL105 Message Format Specifications, release 2026-4 (October 09, 2026). "PDF p." is the page number in the PDF viewer; "printed" is the page number in the document footer.

"Test data is wrong" means a value in the request message (the JSON test data file) breaks a rule written in ATL105, so BUYPASS may reject the message or the test would not prove what it claims.

## Things to confirm (the data values are acceptable)

- **Outdated page cited for the POS Entry Mode table (Table 005)** (TC-001867, TC-001868, TC-001869, TC-001870, TC-001871): The test case cites p.548 for the POS Entry Mode table (Table 005). In ATL105 2026-4, PDF p.548 (printed Appendix H-2) does not contain it; it is on PDF p.555 (printed Appendix I-6). p.548 is where it was in the older 2026-3 edition. ATL105: Appendix I, PDF p.555 (printed I-6). Action: Change the cited page from 548 to 555. The data values are not affected.
- **The quote cited for p.511 is not word-for-word in ATL105** (TC-001867, TC-001868, TC-001869, TC-001870, TC-001871): The test case quotes "03 MasterCard - Authorizer Type: Credit" for p.511. Not word-for-word: all its words are on the cited page, but not in this form. ATL105: Appendix C, PDF p.511 (printed C-1). Action: Quote the text exactly as it appears: "03 MasterCard® Credit".
- **The Terminal Identifier is a placeholder** (TC-001867, TC-001868, TC-001869, TC-001870, TC-001871): The test case flags the merchant as a placeholder (MERCHANT_PLACEHOLDER), so 'JX72948216050257001' was generated, not assigned by BUYPASS. Its State Code (positions 3-4) '72' = Yukon (YT), Canada. ATL105: Element 102, PDF p.417 (printed 13-77); Appendix D, PDF p.517 (printed D-4). Action: Client/BUYPASS to supply the real Terminal Identifier for this merchant and confirm its location.
- **Marked 'ready' although the terminal is a placeholder** (TC-001867, TC-001868, TC-001869): The test case status is 'ready', but its Terminal Identifier is still a placeholder. ATL105: Element 102, PDF p.417 (printed 13-77). Action: Keep the test case out of 'ready' until the real Terminal Identifier is supplied.
- **Same request as TC-001867** (TC-001868): The request is identical to TC-001867 (T1-PUR) except the Sequence Number: same card 510058...7353, expiry 0730, amount $15.00 and entry mode 011. What makes this test different (the device asks for a re-swipe after each of the first three failed reads; after the third failed read it prompts for manual entry of Account Number and Expiration Date (MMYY); the receipt and journal show '*' before the Account Number) happens on the device and is not visible in the message sent to BUYPASS. ATL105: Section 10.1.1.3, PDF p.81 (printed 10-2). Action: Verify on the device: the device asks for a re-swipe after each of the first three failed reads; after the third failed read it prompts for manual entry of Account Number and Expiration Date (MMYY); the receipt and journal show '*' before the Account Number. Optionally use a different card so the logs can tell the two tests apart.
- **The quote cited for p.87 comes from an unrelated section** (TC-001870): The quote is word-for-word, but it comes from Section 10.1.6.1.3 Split Tender Processing (part of 10.1.6 Healthcare Auto-Substantiation Service), PDF p.87 (printed 10-8); that section is about FSA/HRA healthcare benefit cards. ATL105: Section 10.1.6.1.3, PDF p.87 (printed 10-8); Section 10.1.2.1, PDF p.84 (printed 10-5). Action: Cite Section 10.1.2.1 Partial Approval Transaction, PDF p.84 (printed 10-5) as the main basis for a normal MasterCard credit card.
- **Step 1 needs a partial-approval test card** (TC-001870, TC-001871): Step 1 expects Response Code F (partial approval). BUYPASS returns F only when Partial Approval Indicator 1 is sent and the network approves less than the $15.00 requested, so the test needs a card whose available balance is below $15.00. ATL105: Section 10.1.2.1, PDF p.84 (printed 10-5); Element 83, PDF p.404 (printed 13-64); Element 121, PDF p.440 (printed 13-100). Action: Client to supply a partial-approval test card or simulator trigger (the test case is already 'needs_client_input').
- **The Approval Number rule cites the wrong section** (TC-001871): p.85 is Section 10.1.2.2 Authorization Only Reversal Transaction: it covers the Authorization Only Reversal (Transaction Type S, reversing Authorization Only codes 3 and 5), while this step is a Purchase Reversal (Prompt Code 8020, Transaction Type 8). ATL105: Section 10.1.2.2, PDF p.85 (printed 10-6); Appendix G, PDF p.546 (printed G-2); Element 5, PDF p.368 (printed 13-28). Action: Cite Element 5 Approval Number (Chapter 13), PDF p.368 (printed 13-28) instead. The data value itself is correct.
- **Terminal JX72948216050257001 uses more than one terminal capability code (Table 005, position 3)**: code 1 in TC-001867, TC-001868, TC-001870, TC-001871; code 8 in TC-001869. Appendix J note 1 says all transactions from a device use one code. ATL105: Appendix J, PDF p.639 (printed J-2). Action: Use a separate terminal for the RFID test.

## Note for the team that builds the wire message

- **Join Account Number and expiry with '=' in the wire message**: The JSON keeps Account Number and the expiry as separate fields. In the real message for this follow-on transaction they are sent as Account Number, '=', YYMM - not separated by a Field Separator. The Segment Length is the same either way. ATL105: Section 10.1.8.2, PDF p.94 (printed 10-15). The message builder sends 5114395400539140=3107.
