## 1. What was validated

Every field of every test data file was checked against the ATL105 layouts and element definitions (details per scenario in §1 of each findings report):

| Area | Checks |
|---|---|
| Message / Data Section 1 | Message type per step, Element 55 `ATL105`, Element 63 = segments present |
| Segment 100 (17 fields) | Presence, character type, length and valid values; Prompt Code per step role; Segment Length recalculated from the fields plus Field Separators; run-time placeholders |
| Card data (Elements 2 + 12) | Track data, keyed (MMYY), stored credential and follow-on (YYMM) formats per entry mode; card-number check digit and MasterCard range |
| Segment 111 | Tables 005 and 031, and the tables the transaction requires (030 for EMV and Credential on File, 032/049/056 for Credential on File, 003 for AVS) |
| Segment 130 | Elements 187–192 and 118, EMV chip data TLV, cross-field checks (9F02, 9C, 5F34, 9F34, …) |
| Test objective | The data can prove what the test claims (expired card, online/offline PIN, Track 1, AVS, split tender, completion, cancellation, time-out reversal) |
| Step-to-step links | Sequence Number, Account Number, terminal, entry mode and amount against the original step |
| Test case catalog | Expected Response Codes, the test case's own `rule_checks` and `link_defs`, generation fidelity, ATL105 citations |

**How to read each defect section:** a summary table (field, where, type, how many files, actual, expected, ATL105 text, why, how the generator produced it, certainty, fix, check before release), then every affected field with actual vs expected, then numbered steps to confirm it by hand on one example.

Verdicts: **FAIL** violates ATL105 or the test case's own objective · **BLOCKED** holds instruction text that must be replaced by a run-time value · **REVIEW** cannot be decided from the spec or the test data alone (§6).

### D-01 – EMV Card Sequence Number (Element 188) has the wrong width

| Item | Value |
|---|---|
| Field | Element 188 EMV Card Sequence Number (Segment 130) |
| Where in the test data | `"EMV Request Data Segment"` → `"EMVCardSequenceNumber"` |
| Type | Wrong field width |
| Affected | 26 test cases, 28 test data files in 8 scenarios: TS1 Purchase/Capture – EMV Contact Chip; TS2 Purchase/Capture – EMV Contactless Chip; TS11 Authorization Only – EMV Contact Chip; TS12 Authorization Only – EMV Contactless Chip; TS21 Merchandise Return – EMV Contact Chip; TS22 Merchandise Return – EMV Contactless Chip; TS29 Balance Inquiry – EMV Contact Chip; TS30 Balance Inquiry – EMV Contactless Chip |
| Systemic | Yes – found in 28 of the 28 EMV test data files (Segment 130 sent) of the sample (every one): it comes from a generator rule, not from one bad value |
| Actual (generated) | `01` in every affected file |
| Expected (ATL105) | '001' (then recalculate the Segment 130 length) |
| ATL105 reference | Element 188 EMV Card Sequence Number (Chapter 13), p.477 (printed 13-137): *"Fixed length of three bytes, right-aligned and padded with zeroes"*<br>Element 188 EMV Card Sequence Number (Chapter 13), p.477 (printed 13-137): *"Valid Codes/Values: 000—099 EMV Card Sequence Number is supplied by the EMV chip card"* |
| Why it is wrong | Element 188 is fixed at 3 bytes, right-aligned and zero-filled. The chip data carries Tag 5F34 = '01', so the card sequence number itself is right, but '01' is 2 bytes; it must be '001'. The declared Segment Length (1181) was calculated with the 2-byte value and changes by +1 when corrected. (TC-001722) |
| How the generator produced it | `method: realistic_emv_card_sequence` (28 of 28 files) – flags: `EMV Card Sequence Number = Tag 5F34 of the same card (element 188, p.270)` |
| Certainty | Certain |
| Fix in the generator | Element 188 = Tag 5F34 right-aligned and zero-padded to 3 digits (`01` → `001`); 3 spaces when Tag 5F34 is absent. Recalculate the Segment 130 Segment Length afterwards. |
| Check before release | Element 188 has 3 characters and equals Tag 5F34 zero-padded |

'62862543' ($628,625.43) has 8 digits. MasterCard amounts allow at most 7 digits; 8 digits are allowed for American Express cards only.
4. The completion amount cannot be larger than the original authorization: [test_cases.jsonl line 302](../mastercard_credit/test_cases/test_cases.jsonl#L302) → `steps[1].request` → `Nonfuel Amount` (used for TD-TC-002023.step2.completion.json) = `62862543`. The completion must carry exactly the amount approved in step 1. A partial approval is always less than the $15.00 requested, so '62862543' ($628,625.43) is impossible.
5. Segment Length was calculated from the invalid test case value: [TD-TC-002023.step2.completion.json](../mastercard_credit/test_data/TD-TC-002023.step2.completion.json#L7) line 7 = `088`. With real values (amount 1 to 4 digits; Approval Number always 6 characters) the Segment Length can only be 081 to 084, so '088' can never be correct.
6. Read in ATL105: Element 58 Nonfuel Amount (Chapter 13), p.393 (printed 13-53): *"A maximum length of 7 bytes is allowed for all other card types."*; Section 10.1.2.1 Partial Approval Transaction, p.84 (printed 10-5): *"Approved Amount (Element No. 6) contains the approved partial amount, and the POS device must prompt for payment of the remaining balance due on the sale."*; Element 121 Partial Approval Indicator (Chapter 13), p.440 (printed 13-100): *"the network can approve an amount that is less than the amount in the Authorization request"*; Element 6 Approved Amount (Chapter 13), p.368 (printed 13-28): *"Fixed length of nine digits with two assumed decimal places Zero-filled and right aligned"*; Section 12.1 Standard Message Data Segment, p.223 (printed 12-6): *"Identifies the data segment's length, including Segment Type's length and Field Separators."*; Element 84 Segment Length (Chapter 13), p.406 (printed 13-66): *"This figure is calculated using the lengths of all data elements in the segment plus all Field Separators/Product Data Field Delimiters related to those elements."*
7.
