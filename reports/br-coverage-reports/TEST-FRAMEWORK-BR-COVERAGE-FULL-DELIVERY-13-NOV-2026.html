Executive summary

70.55% of the test framework's own oracle rules now have a candidate match

Of the test framework's 601-rule oracle catalog — the rule set actually checked into regression-artifact-validator/specifications/ATL105/docs/specs/kb/, spanning all 49 trained ATL105 segments — 424 (70.55%) have at least one candidate match at or above the matching floor, sourced from 67,167 text items (16,040 distinct texts after deduplication) across all 99 packages in the 31-Oct full-sweep delivery. 140 (23.29%) reach the stronger Semantic or Strong tiers.

What this number is, and is not

This is an automated candidate-reach measure: shared, IDF-weighted vocabulary (and, for a Strong candidate, a literally shared ATL105 section or segment number) between an oracle rule's own title and at least one AI delivery statement. It is not SME confirmation, not semantic equivalence, and not evidence the delivery actually implements or tests that requirement — every one of these 601 rules is itself still businessRuleStatus: DRAFT_REVIEW_REQUIRED in the framework's own records, with 0 of 601 SME-approved.

Confirmed, not assumed: which content type actually drives the 424 matches

420 of 424 best matches (99.1%) are sourced from scenario_supporting_rules.csv statements — this is overwhelmingly the signal. business_requirements.json content (BR names, citations, exclusion reasoning), which was the entire numerator last pass, drives only 4 of 424 best matches against this denominator too. business_scenarios.json scenario names drive 0. The lesson holds across both denominators: atomic rule-paraphrase text (scenario_supporting_rules.csv) is the numerator source that actually reaches an atomically-written Test BR catalog; summary-level BR/scenario naming is not, regardless of which catalog you check it against.

What's still unreached, and why

The remaining 177 unmatched rules cluster in wire-protocol and meta-structural rules, not business logic

Reading the unmatched rows directly (not inferring from counts): the largest shares are field (85), serialization (25), structure (15), compatibility (9), (none) (9). Concretely, many are TCP/IP transport-header rules (“TCP/IP message length uses network byte order”, “TPDU Protocol ID is 0x60”) and meta-structural rules about the message format itself (“Unknown segment combinations require review”, “Empty non-trailing fields retain separators”) — categories a test-case generator working at the business-scenario level would not be expected to paraphrase, since they describe wire-protocol mechanics below the scenario/transaction layer the AI delivery operates at. This is a believable, structurally-explained gap, not an unexplained anomaly.

Known limitations

Read this before citing a single headline number

  • No independent per-rule review status to cross-check against. Unlike the prior 1,343-row catalog (which had a Status field ranging from COVERED to REVIEW_REQUIRED, letting candidate reach be sanity-checked against it), every one of these 601 rows shares the same businessRuleStatus: DRAFT_REVIEW_REQUIRED and 0 SME-approved rules. The match-quality cross-check used instead here is the rule class breakdown (see above) and direct worked examples, not an independent status signal.
  • 30 of 601 oracle rules (5.0%) are SHORT-flagged (fewer than 3 meaningful tokens after stopword removal), e.g. “Segment Type is 100”. These remain the least reliable matches in this report, the same as in every report in this series.
  • Spec-version note: every row in this 601-rule catalog cites ATL105 2026-3 section/segment numbers (per sourceAnchor.specification/version); this delivery is built against 2026-4. The same caveat applied, unremarked, to the prior crosswalk's 1,343-row catalog.
  • scenario_supporting_rules.csv required a non-obvious per-package filter. The file is a shared master list of 1,919 candidate rules, identical across every one of the 99 packages; only rows with scenario_count > 0 are actually applicable to that package's own scenarios. This was caught and corrected before matching — an initial unfiltered extraction over-counted the numerator by roughly 3×.
  • This is still a candidate-reach measure, not approval. A Strong or Semantic candidate means the AI's own delivered text plausibly addresses the same topic as an oracle rule — it does not mean a test case actually exercises and asserts that rule correctly (see the companion 12-Nov full-sweep validation report for execution-level defects in this same delivery, e.g. N12-01).

Methodology

How the match score is computed

  • Denominator: all 601 rows of atl105-br-approval-matrix.json (oracleRuleCount: 601), itself a consolidated view of the 49 individual segment-*/coverage/segment-*-rule-catalog.json files checked into the regression-artifact-validator test framework — the same catalog this workspace's own coverage_engine.py already treats as the Test Solution rule baseline. Every row counted, none excluded.
  • Numerator: every package's pack/business_requirements.json (BR name, citations, excluded-combination reasoning — as in the prior pass), pack/scenario_supporting_rules.csv (statement text, filtered to scenario_count > 0 rows only), and pack/business_scenarios.json (scenario names), across the 99 unique (program, network) packages resolved from the 104 build directories under Downloads\builds\builds. 67,167 raw items, deduplicated by exact normalized text to 16,040 distinct texts before scoring.
  • Tokenization, IDF weighting, scoring and tiers: unchanged from the prior two reports in this series — lowercase/punctuation-stripped tokens, the same stopword list, idf(token) = log((N+1)/(df+1)) + 1 computed over the 16,040 deduplicated numerator texts, score = 0.5×weighted overlap coefficient + 0.5×weighted recall, +0.15 for a shared section/segment-number anchor. Weak ≥ 0.35, Semantic ≥ 0.55, Strong ≥ 0.70 + anchor.
  • Matching is exhaustive, not approximated: all 601×16,040 = 9,640,040 pairs were scored directly (runtime: under 10 seconds).
  • Per-rule result = its single best-scoring AI item across all 99 networks combined (shown in the appendix); per-program reach is computed separately as a yes/no (does any network in that program clear the floor for this rule).

What this does and doesn't tell you

70.55% is the candidate-reach of the full 99-network delivery's own delivered text (BRs, supporting rules, scenario names together) against the test framework's own 601-rule oracle catalog — the right denominator per the request that produced this rebuild, and a legitimate, substantially higher number than the prior pass because both the denominator (smaller, better-aligned) and the numerator (now 2.7× larger, specifically including the atomic rule-statement corpus) changed for defensible reasons, not because thresholds or scoring were loosened.

Recommended next step: route the 20 Strong-candidate and 120 Semantic-candidate rules to SME review first (highest automated confidence, excluding SHORT-flagged rows). Treat the 177 unmatched rules as the real structural gap list — concentrated in wire-protocol/meta-structural rules the AI delivery operates above, per the analysis above — and confirm with the test framework owners whether those categories are in scope for AI-generated test content at all, or are expected to remain framework-only concerns.
